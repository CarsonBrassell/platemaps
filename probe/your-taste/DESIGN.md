# Your taste (Discover recs) design, 2026-10-27, NOT APPROVED, mockup first

## name
Your taste: a private picks section at the top of Discover (web + phone)

## summary
Add a 'Your taste' section above the Discover grid on web and phone. It shows up to 12 places you have not been (expandable to 24), ranked by the cuisines you picked, the cuisines of places you have posted at or marked 'Been here', where your friends have posted, and place quality. Each card carries one honest reason line ('Sam posted here', 'You picked Burgers', 'You've been to 3 Sandwiches places') plus two small buttons, 'Been here' and 'Not for me'. It is the MVP's standalone private route and single shared scorer, with the user design's explicit picks and been-here marks grafted on and the signal design's quality formula and enrichment seam; it does not touch the cached Discover GET or the filter pipeline. With no signal it shows only a compact cuisine-chip invite and never fakes picks.

'See all' expands in place to a grid of up to 24 from the same payload (no second request). Header, a horizontally scrolling chip row (same pattern as PhoneFilterBar), then a snap scroller (px-4 gap-2) of PhoneRestaurantCardGrid at ~44vw with the same reason line and buttons (44px hit area). No-signal state is a compact one-row chip invite on both surfaces. Nothing in the h1, the sticky bar or the static shells (src/app/page.tsx, src/app/m/page.tsx) changes.

## preferences_input
Explicit, all private to the viewer: (1) 'I love' cuisines, max 5, chips taken from page.options.cuisines (the 29 real cuisines already on the page; NOT src/data/restaurantFacets.ts, which has 16 entries of which only 10 are real). (2) 'Not into' cuisines, max 5, disjoint from loves; applies only inside Your taste. (3) Per card 'Been here' (place leaves the list and counts as eaten) and 'Not for me' (place hidden), with a one-slot Undo for the last action; 'Reset my taste' in the Edit panel clears everything. Implicit: restaurantIdsPostedBy (db.ts:1539), mutual friends' hero posts, and users.favorite_cuisine only when it matches a real corpus cuisine (used as a virtual love; 1 of 22 users has it). Storage: signed in = new taste_prefs row (loves, skips, been, hidden), written only through a session-only route that takes no user id (same rule as /api/account/flavor-profile route.ts:9-10). Signed out = localStorage 'pm.taste.v1' (try/catch) sent in the POST body, validated against the corpus and never stored server-side. On first signed-in load with no server row, the hook uploads the local copy once, then clears it. Not collected: price, dietary, spice, ratings, hearts, upvotes, saves.

## scoring
Pure function in src/lib/taste.ts over loadCorpus() (discover.ts:209: ~9,023 listed rows, plates). Candidates = every listed row; no rating or photo gate (listing gate stays hold_reason IS NULL plus coordinates).

1. visited = restaurantIdsPostedBy(user) U been. Drop visited, hidden, and any cuisine in skips. Skips apply only here.
2. A (cuisine affinity, 0-1). pick_c = 1 if c in loves (loves includes a valid favorite_cuisine). hist_c = distinct visited restaurants in c / max over cuisines of that count (counted per place, not per post, so one place with 10 posts cannot dominate; cuisine read from the corpus row, no SQL join). History counts only when visited places with a cuisine >= 3 (MIN_POSTS, tasteMatch.ts:66). A = 0.6*pick + 0.4*hist when both exist, else whichever exists. A = 0 when restaurants.cuisine is NULL (159 rows).
3. F (friends, 0-1) = min(1, F_count/2), F_count = distinct mutual friends with a hero post (meal_id IS NULL) at the place. Friends = getFriendIds (db.ts:2277) minus getBlockedEitherWayIds (db.ts:2505), via a new getFriendRestaurantVisits(viewerId).
4. Q (quality, 0-1). If PlateScore.ready (>=3 rated dishes and >=8 ratings): 0.6*clamp((plate% - 60)/40) + 0.4*sourceTerm, else 0.8*sourceTerm. sourceTerm = clamp((rating - 3.8)/1.2, 0, 1) * min(1, log10(1+reviewCount)/2.5), so 4.6 stars with 800 reviews beats 5.0 with 3. Unrated places get Q = 0.3, never excluded. Sourced ratings are nearly flat (6,929 of 8,013 in [4,5)), so Q mostly picks the better place inside a cuisine; the viewer never sees it as a score.
5. N (neighborhood, 0-1) = visited places in r.neighborhood / max over neighborhoods; 0 with no visits.

SCORE = 100 * (0.50*A + 0.20*F + 0.20*Q + 0.10*N). Require A > 0 or F > 0 so no-signal places never pad the list. Price is deliberately out of v1 (880 of 9,023 rows, 9.8%, have a price band). The 'trending' (Promoted, 67 rows) flag is never used.

SELECT: sort by score desc, ties by has-photo then corpus sort_order; take greedily up to limit (default 24, max 24) with at most 1 per chain key (first two normalized name tokens minus leading 'the', plus cuisine; handles Rubio's, Tajima Ramen branches, Mendocino Farms) and, only when >= 2 cuisines have A > 0, at most ceil(0.4*limit) per cuisine (offsets Mexican 1,383 and Coffee & Tea 1,122 of 9,023). If fewer than 6 survive, return only those. All weights live in one const table. Enrichment seam: restaurantTraits(r) returns [{cuisine, weight}]; v1 returns [{r.cuisine, 1}], later main 1.0 + secondary 0.4 each, A(r) = max weight*A(cuisine). Cost: one in-memory pass over ~9k rows plus ~5 small indexed queries run in parallel (prefs, posted ids, friend ids, blocked ids, friend visits); the corpus is already warm.

## cold_start
Server returns basis, and the UI shows exactly that and nothing more. 'history': >= 3 visited places with a cuisine, header 'Based on 7 places you've been and 2 picks'. 'starting': 1-2 visited places or any picks/favorite, same formula, header 'Based on your picks and first plates'; with <3 visited, visits only exclude and feed reasons, they do not move the ranking. 'friends': no visits and no picks but mutual friends have posted (10 viewers today, median 17 candidates, max 28), header 'Where your friends eat'. 'none': no signal, which is most signed-out visitors and new accounts (today only 10 of 22 users have any positive signal, 4 have >= 3 posts): picks = [], the section collapses to a compact 'What do you like?' one-row chip invite (top 10 cuisines by count plus More) and a 'Post a plate' link (/post or /m/post). One chip tap writes the pick, refetches, and the section fills (basis 'starting'). Signed-out visitors need no wall (OPEN_BROWSING = true, signInGate.ts:51); a quiet 'Sign up to keep your picks across devices' link uses signInHrefFor with a new signInPromptFor line. Layout: / and /m are static (revalidate = 60) and cannot read the cookie, so the section is client-fetched after useAuth().resolved; SSR a fixed-height skeleton so the grid below does not jump, and render the chip invite instantly (no fetch) when signed out with empty local picks.

## reasons_shown
One line under each card, the single strongest contributor, built server-side in taste.ts and returned as reason {kind, text} so web and phone cannot drift. Priority: friend, then picks/history/favorite, then neighborhood. Patterns: friend 'Sam posted here' or 'Sam + 2 friends posted here' (mutual friends only, names from posts.author_name); picked 'You picked Burgers'; favorite 'Your favorite cuisine: Sandwiches'; history 'You've been to 3 Sandwiches places' (real count, posted plus been-here marks); neighborhood fallback 'In Pacific Beach, where you eat'. The verbs are only picked, been to and posted, never 'liked' (no like or rating feeds the score). No percentage or score is shown (false precision at 22 users). Header basis line is derived from the same profile object as the cards, so they cannot disagree. 'Been here' and 'Not for me' say what they do: they affect Your taste only. Friend reasons appear only for friends the viewer already sees in getFriendsFeed (db.ts:1443), minus blocks either way.

## data_changes
One additive table, appended to the statements array in scripts/migrate.mjs (idempotent, no snapshot needed, but ask Calvin before running it against Neon per the RESUME.md:17 pattern): CREATE TABLE IF NOT EXISTS taste_prefs (user_id TEXT PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE, loves TEXT[] NOT NULL DEFAULT '{}', skips TEXT[] NOT NULL DEFAULT '{}', been TEXT[] NOT NULL DEFAULT '{}', hidden TEXT[] NOT NULL DEFAULT '{}', updated_at TIMESTAMPTZ NOT NULL DEFAULT now()). Restaurant ids are TEXT with no FK (a later-held place is harmless; ids not in the corpus are ignored). Arrays capped server-side (loves/skips 5 each, been/hidden 300 each). Nothing else in Neon changes: no backfill, no enrichment load, Denver data untouched, post_hearts never read. One new SELECT-only helper, getFriendRestaurantVisits. Docs: PrivacyDocument.tsx:116 currently says 'any preferences you set (like a favorite cuisine)'; add the picks and the been-here / not-for-me marks. If Calvin declines the schema, the same design ships with localStorage for signed-in users too (only the prefs source changes; scorer, route shape and UI are identical).

## risks
- Prior decisions (RESUME.md:16-17): 'do NOT build recs' and the new taste model is 'Not approved to build yet'; like-score radar and Taste Wheel were cancelled. This design counts visits and picks only (no ratings, likes, hearts, upvotes, saves) and per memory a mockup must be shown and approved before any code, and the migrate needs Calvin's go-ahead.
- Thin data: 22 users, 7 with posts, 4 with >= 3 posts, 10 with any signal. Most people see the chip invite or friends mode first. That is correct behavior, but the demo needs a seeded account, and copy must not oversell ('Based on your picks', never 'we know your taste').
- It is a section, not a filter: it hides under any filter, search or Nearby and cannot combine with neighborhood. A combinable 'Your taste' filter would need a QuickFilter plus routing useDiscoverQuery to a private POST (the public GET is CDN-cached by query string, s-maxage=60, and must never carry personal results); roughly L. Ask Calvin which he means by 'find places'; this design takes the section reading.
- Chain and cuisine noise: restaurants.cuisine is one of 29 values, 159 listed rows are NULL, and chains carry mixed tags (Mendocino Farms: 7 Sandwiches, 1 Vegetarian). The chainKey heuristic (two name tokens plus cuisine) and the 40% cuisine cap mitigate this but must be verified against the corpus in check-taste.mjs.
- Proxy checked (src/proxy.ts ~97-105): cookie-less /api/ calls get 401 unless isPublicPath is true, and signInGate.ts:69-73 returns true for /api/* while OPEN_BROWSING is true, so signed-out POSTs work today. If OPEN_BROWSING is flipped off, the hook must treat a non-OK response as 'hide the section, keep local-only chips' rather than error.
- Privacy: friend reasons expose friends' visits, so mutual friends only, blocks applied both ways, session-only route with no user id, marks never shown on profiles, feeds or to friends, and post_hearts never joined (migrate.mjs:122,160).
- Name collision: the Feed tab already uses 'For You' (PRODUCT.md:41); use 'Your taste'.
- Layout shift and auth timing: the shell is static, so the section is client-fetched after useAuth().resolved; SSR a fixed-height skeleton and render the empty-state chips without a fetch to avoid the grid jumping.
- Stale favorite-cuisine picker (src/data/restaurantFacets.ts: 16 entries, 10 real) feeds settings, so the taste chips read live options.cuisines instead, and favorite_cuisine is used only when it is a real corpus cuisine. Fixing the settings picker is separate scope.
- Price dropped from v1 (880 of 9,023 rows have a band); dietary stays out (profiles.json is {}, nothing in Neon, 1,939 listed restaurants have no menu, Terms :243/:327 disclaim dietary advice). Both are revisited only after Calvin approves the enrichment load via the restaurantTraits seam.
- Semantics of Hide / Been here: they affect Your taste only, so users may expect regular Discover to change. Copy must say so; no Restore list in v1 (only last-action Undo and Reset), a v2 item. Optimistic removal plus refetch must not visibly reorder the remaining cards.
- Thin photo coverage (1,624 of 9,023 listed have photos) will make crop-shape strip cards look bare; photo is only a tie-break, never a gate, and the mockup should show a photo-less card honestly.
